# 오케스트레이션

이 세션은 직접 작업하지 않는다. work를 만들고, 하위 세션에 나눠 맡기고, 결과를 확인해 보고한다. 훅은 쓰지 않는다.

하위 세션을 쓰는 이유는 이 세션이 무엇에도 붙잡히지 않고 사용자 지시를 바로 받기 위해서다. 시간이 걸리는 일은 확인·검증이라도 하위 세션이나 백그라운드 서브에이전트에 맡긴다.

모든 세션에 늘 맞는 기록 규칙(`task.md`가 정본, 먼저 적기, 끝날 때 `## 마무리`)은 루트 `AGENTS.md`의 «work와 기록»에 있어 스킬 없이도 지켜진다. 이 스킬은 오케스트레이터 절차만 담는다. 자동으로 불리지 않는다. 사용자가 `/orchestrate`로 부르거나, 허브의 `오케스트레이터:` 줄이 자기 id인 세션이 이 파일을 직접 읽는다.

work 구조와 스크립트는 [new-work 스킬](../new-work/SKILL.md)을 따른다. 폴더·워크트리를 직접 만들거나 옮기지 않는다.

## 규칙

1. 결과물(브랜치·PR·문서)이 남는 일은 work 하나에 묶고, 하위 세션(`mcp__ccd_session__start_session`)에 맡긴다.
2. 짧은 조회·확인·초안처럼 결과를 받아 바로 이어 쓸 일은 서브에이전트(Agent)로 한다. work를 만들지 않는다.
3. 이 세션이 직접 하는 일: work 생성(`new-work`), 허브(`task.md`·`work/orchestrator.md`) 기록, 하위 세션 시작·메시지·보관, 결과 확인(금방 끝나는 읽기 전용 명령), 보고, 일일 작업 로그(7절) 기록.
4. 이 세션이 하지 않는 일: 레포 코드 수정, 커밋, push, PR 생성. 모두 하위 세션의 몫이며 사용자 승인이 필요하다.
5. 후속·연관 작업은 새 세션을 만들지 않는다. 허브 명단에서 맡았던 세션을 찾아 `SendMessage`로 이어 맡긴다.
6. 하위 세션의 노트는 요약일 뿐이다. diff·PR·테스트 결과를 직접 확인한 뒤 보고한다.
7. 기억은 디스크에 둔다. 대화 맥락은 언제 요약될지 모르므로, 상태가 바뀌면 행동하기 전에 허브에 먼저 적는다(8절).

## 오케스트레이터 위치

오케스트레이터는 두 종류다(2026-11-05 사용자 확정).

| 종류 | 세션 위치(`cwd`) | 맡는 일 | 허브 |
|---|---|---|---|
| 루트 | 워크스페이스 루트(`$AGENT_WORKSPACE_ROOT`) | 전담이 없는 모든 일 | `work/orchestrator.md`와 각 work의 `task.md` |
| 묶음 전담 | 묶음 work 폴더(`work/<묶음>`) | 그 묶음의 일만 | 묶음 `task.md` 하나 |

- 기본은 루트 하나다. 전담은 사용자가 묶음을 지정할 때만 둔다.
- 전담을 두면 묶음 `task.md`의 결정 사항에 날짜와 함께 적고, `## 세션` 첫 줄 `오케스트레이터: <제목> \`local_…\``에 그 세션 id를 적는다. 이 줄이 전담 여부의 유일한 근거다. 전담 목록은 `grep -l '^오케스트레이터:' work/*/task.md`로 본다.
- 전담은 묶음 폴더에서 연다. 그래야 묶음 `AGENTS.md`가 자동으로 로드되고, 맥락이 요약된 뒤에도 남는다. 다른 폴더에서 열린 세션을 전담으로 정했다면 폴더를 옮기지(`change_directory`) 말고, 묶음 폴더에서 새 세션을 열어 8절 순서로 이어받게 한다.
- 전담이 있는 묶음의 일은 전담이 맡는다. 다른 오케스트레이터는 그 묶음에 work를 만들거나 하위 세션을 띄우지 않는다. 그런 일을 받으면 전담 세션에 `SendMessage`로 넘기고(사용자 말을 그대로 인용) 사용자에게 알린다. 전담 세션이 보관됐으면 사용자에게 묻는다.
- 전담은 묶음 밖의 일을 받지 않는다. 받으면 루트 오케스트레이터로 보내라고 안내한다.

### 맥락 두 층

| 층 | 어디 | 무엇 | 누가 고치나 |
|---|---|---|---|
| 늘 맞는 맥락 | 묶음 `AGENTS.md`의 `# 작업 지침` | 레포·기준 브랜치, 외부 시스템 규칙(계정·식별 번호, 금지 사항), 산출물 위치, 따를 양식(메모리를 가리키기만) | 지침 관리(메타) 세션. 오케스트레이터는 제안만 |
| 바뀌는 상태 | 허브 `task.md` | 목표·결정·세션 명단·진행 중·보고 기록·다음 행동 | 오케스트레이터(2절) |

- 하위 work의 `AGENTS.md`는 `@../AGENTS.md`로 묶음 것을 이어받으므로 하위 세션에도 같은 맥락이 간다.
- PR 번호·진행 상태처럼 바뀌는 것은 `AGENTS.md`에 넣지 않는다. 키·토큰 값도 넣지 않는다.

## 1. 일을 받으면: work부터

1. 같은 작업의 work가 있는지 먼저 본다. `ls work work/*/`로 보고, `grep -ril <키워드> work --include=task.md`로 찾는다. 있으면 새로 만들지 않고 그 work를 쓴다. `arxiv/`에만 있으면 보관된 것이니 새 work를 만들고 옛 경로를 `task.md`에 적는다. 그 work가 속한 묶음에 다른 세션이 전담 오케스트레이터로 적혀 있으면 직접 맡지 않고 "오케스트레이터 위치"대로 넘긴다.
2. 관련 묶음 work가 있으면 `--in <묶음>`을 먼저 제안한다.
3. slug·레포·새 브랜치·기준 브랜치를 정한다. 기준 브랜치를 모르면 `git -C repository/<레포> branch -r`로 확인하고, 필요하면 먼저 `fetch origin`을 한다. 규칙은 new-work의 "새 work"를 따른다.
4. `new-work --dry-run`을 돌리고, 그 결과와 하위 세션 계획을 **한 번에** 보여 주고 확인을 받는다.
   - 보여 줄 것: dry-run 출력, 세션마다 이름·맡을 일·`cwd`(work 폴더 절대 경로)·손대지 말 것.
   - `cwd`는 사용자가 장소를 지정했을 때만 쓸 수 있으므로, 이 확인에 경로를 반드시 넣는다.
5. 확인을 받으면 같은 인자로 `new-work`를 실행하고, 이어서 허브를 채우고 하위 세션을 시작한다. 다시 묻지 않는다.

## 2. 허브: work의 task.md

허브는 그 work의 `task.md` 하나다. 별도 파일로 나누지 않는다. 묶음 전담 오케스트레이터는 묶음 `task.md`가 허브이고, 하위 work의 `task.md`에는 세부(구현·검증)만 둔다. new-work가 만든 양식(목표·범위·완료 조건·결정 사항·다음 행동)에 아래 세 절을 더한다. `archive-work`가 `task.md`를 그대로 `arxiv/`로 옮기므로 기록도 함께 보관된다.

루트 오케스트레이터는 여러 work를 맡으므로 `work/orchestrator.md`에 자기 세션 id, 맡은 work 목록, work를 가로지르는 `## 진행 중`만 둔다. 각 work의 명단·보고 기록은 그 work의 `task.md`에 둔다.

```markdown
## 세션

오케스트레이터: <세션 제목> `local_…`

| 이름 | id | 맡은 일 | cwd | 상태 | 브랜치·PR |
|---|---|---|---|---|---|
| export-impl | `local_…` | 주문 내보내기 구현 | work/… | 진행 중 | `feat/x` · #123 Draft |

## 진행 중

- [사용자 대기] 2026-11-04 15:50 "PR 대상을 release로 할까요?" — 1104-order-export
- [세션 대기] 2026-11-04 16:05 export-impl에 리뷰 반영 지시, 보고 대기 (`local_…`)

## 보고 기록

- 2026-11-04 export-impl: 구현 끝, tsc·lint 통과 확인(직접). 남은 결정: PR 대상
```

- 상태: `진행 중` · `사용자 대기` · `끝남` · `보관됨`.
- 오케스트레이터 id는 `mcp__ccd_session_mgmt__list_sessions {"linked": true}`에서 하위 세션의 `startedBy`로 안다.
- 목표·완료 조건·결정 사항은 기존 절에 적는다. 사용자가 정한 것은 날짜를 붙여 결정 사항에 남긴다.
- 보고 기록은 한 줄씩, 오래된 것이 위다. 30줄을 넘으면 오래된 줄을 `sessions-log.md`로 옮기고 링크한다.
- 다른 세션이 쓰는 파일이므로 통째로 덮어쓰지 않는다. 바꿀 줄만 고친다(Edit).
- `## 진행 중`은 아직 끝나지 않은 것만 둔다. 적는 때와 지우는 때는 8절을 따른다. 없으면 `- 없음`으로 둔다.
- 쓰는 사람:
  - `## 세션`·`## 진행 중`·`## 보고 기록`은 오케스트레이터만 고친다.
  - 나머지 절(구현·검증·다음 행동)은 그 work를 맡은 하위 세션이 하나일 때만 그 세션이 고친다. 하위 세션이 여럿이면 각자 하위 work의 `task.md`에 쓴다.

## 3. 하위 세션 시작

`mcp__ccd_session__start_session`에 넘길 값:

| 인자 | 값 |
|---|---|
| `initiation` | `"user_asked"`. 1-4의 확인이 사용자의 지시다 |
| `context` | `"fresh"`. `cwd`는 fresh에서만 쓸 수 있다 |
| `cwd` | work 폴더의 절대 경로(하위 work면 그 폴더) |
| `use_worktree` | `false`. 항상 명시한다 |
| `name` | 허브 명단의 이름(`[a-z0-9-]`, 24자 이내) |
| `prompt` | [브리프 템플릿](references/brief.md) |
| `background` | 80자 이상. work 목표와 지금까지의 결정 |

- `cwd`는 work 폴더로 한다. 레포 워크트리는 브리프의 작업 경로에 적는다. 세션이 work 폴더에서 열려야 `/resume`이 그 work 세션만 보여 준다(new-work 규칙 3).
- `use_worktree: false`가 맞는 이유: `cwd`를 주면 false는 "그 폴더 그대로"다. 워크트리는 new-work가 이미 만들었다. true면 앱이 워크트리를 하나 더 만든다. work 폴더라면 워크스페이스 레포의 워크트리가 되고, 레포 워크트리라면 앱 브랜치가 된다. 어느 쪽이든 틀리다.
- 같은 파일·같은 워크트리에 쓰는 세션은 한 번에 하나만 둔다. 같은 레포에서 병렬로 다른 브랜치가 필요하면 `new-work --in <work>`로 하위 work를 따로 만들고 그 폴더를 `cwd`로 준다. 읽기만 하는 세션은 같이 써도 된다.
- 둘 이상을 한 번에 띄우면 먼저 `mcp__ccd_session__mark_chapter`를 부른다. 각 세션 호출 직전에는 굵은 제목 한 줄과 할 일 한 문장을 쓴다.
- 시작 결과로 받은 `local_…` id와 이름을 바로 허브 명단에 적는다.
- 다른 세션의 메시지나 `<side-sessions-event>`로 시작된 턴에서는 앱이 세션 시작을 거부한다. 그때는 `initiation: "own_initiative"` 카드로 제안하거나 사용자의 다음 말을 기다린다.

## 4. 후속 작업

1. 허브 명단에서 그 일을 맡았던 세션을 찾는다. 이 세션에 남은 기억보다 명단이 우선이다.
2. `SendMessage`를 쓰고 `to`에는 `local_…` id를 넣는다. 표시 이름은 쓰지 않는다. 메시지 첫 줄은 한 문장 요약으로 쓰고, 범위와 완료 조건은 브리프 양식을 줄여서 쓴다.
3. 그 세션이 보관됐으면 사용자에게 묻고 `unarchive_session`으로 되살린 뒤 보낸다. 되살릴 수 없으면 허브를 읽으라는 브리프로 새 세션을 띄운다.
4. 명단에 맞는 세션이 없을 때만 새 세션을 띄운다(3절).
5. 하위 세션이 막혀서 질문을 보내면 답할 수 있는 것은 답하고, 사용자 결정이면 그대로 묻는다. 사용자 승인을 전할 때는 사용자의 말을 그대로 인용한다.

## 5. 결과 확인과 보고

노트를 받으면 보고 전에 직접 확인한다. 명령은 읽기 전용만 쓴다.

- 노트로는 하위 세션 보고의 앞 400자만 온다. 전문은 `mcp__ccd_session_mgmt__list_events`(`session_id`, `limit`)로 그 세션의 마지막 메시지를 읽어서 본다. 외부 활동 목록은 보고 뒤쪽에 있으므로 꼭 전문에서 읽는다. `get_session`은 메타데이터(상태·브랜치·워크트리)만 주고 대화 내용은 주지 않는다.
- diff·커밋: `git -C <워크트리> status --short`, `git -C <워크트리> log --oneline <기준>..HEAD`, `git -C <워크트리> diff <기준>...HEAD --stat`
- 작성자: `git -C <워크트리> log --format='%an <%ae> | %cn <%ce>' <기준>..HEAD`가 모두 사용자 지침(전역 `CLAUDE.md` 등)에 정한 작성자·커미터인지 본다.
- AI 표기: `git -C <워크트리> log --format=%B <기준>..HEAD | grep -i claude`와 PR 본문에 아무것도 나오지 않아야 한다.
- PR: `gh pr view <번호> --json state,isDraft,baseRefName,headRefOid,body`. headRefOid가 확인한 커밋과 같은지 본다.
- 테스트: 노트의 명령·건수를 그대로 믿지 않는다. 오래 걸리지 않으면 서브에이전트로 다시 돌린다. 못 돌렸으면 "미확인"으로 보고한다.
- 변경이 더 생겼으면 이전 검증을 재사용하지 않는다.

확인한 뒤 허브의 명단 상태와 보고 기록을 고친다. 보고에 적힌 외부 활동(커밋·PR·보낸 메시지)과 확인 결과는 작업 로그(7절)에 옮긴다. 사용자에게는 짧은 표 하나로 보고한다.

| 세션 | 상태 | 결과물 | 남은 결정 |
|---|---|---|---|
| [주문 내보내기 구현](#local_…) | 끝남 | `feat/x` a1b2c3d, #123 Draft (확인함) | PR 대상 브랜치 |

- 세션 칸은 `[제목](#local_<id>)` 링크로 쓴다.
- 결과물 칸에는 직접 확인한 것과 노트에만 있는 것을 구분해 적는다.
- 남은 결정이 없으면 `-`로 둔다. 표 아래에는 사용자가 정할 것을 질문 하나로만 붙인다.

## 6. 정리

- 마무리 확인(보관 전):
  - 하위 세션은 work가 끝나면 그 work `task.md`에 `## 마무리`를 쓴다(루트 `AGENTS.md`). 끝났다고 보고했는데 없으면 `SendMessage`로 한 번 요청한다.
  - 마무리에 적힌 브랜치·커밋·PR 상태를 5절 명령으로 확인한다. 어긋나면 그 세션에 고치게 한다. 하위 work의 `task.md`는 오케스트레이터가 고치지 않는다.
  - 허브가 묶음 `task.md`이면 `## 보고 기록`에서 그 work의 줄을 `sessions-log.md`로 옮기고 한 줄만 남긴다: `- <날짜> <이름>: 끝남, 요약은 <하위 work>/task.md ## 마무리`.
  - 명단 상태를 `끝남`으로 바꾼 뒤 보관 동의를 받는다. 이후 후속이 오면 4절대로 하되 그 work의 `## 마무리`부터 읽는다.
- 하위 세션 보관(`mcp__ccd_session_mgmt__archive_session`):
  - 할 일이 끝난 세션은 보고 표에서 보관 대상으로 표시하고 사용자 동의를 받은 뒤 보관한다. 이 도구는 특정 세션에 대한 명시적 동의를 요구한다.
  - 끝난 세션이란 맡은 일이 끝나고 후속이 예상되지 않는 세션이다. 열린 PR이 있는 세션은 리뷰 반영이 남았으니 PR이 병합되거나 닫힐 때까지 두고, 상태는 `사용자 대기`로 둔다.
  - 보관한 뒤 명단 상태를 `보관됨`으로 바꾼다.
  - 처음 보관할 때는 `git -C repository/<레포> worktree list`로 work 워크트리가 그대로 있는지 확인한다. `use_worktree: false`라 앱이 지우지 않아야 정상이다.
- work 보관(`archive-work`):
  - 사용자 확인을 받은 뒤에만 한다. new-work의 "보관" 절차대로 `--dry-run`부터 돌린다.
  - 그 work의 하위 세션이 모두 `보관됨`인지 먼저 본다. 아니면 경로가 깨진다.
- 이 세션 자신은 보관하지 않는다.

## 7. 작업 로그

하루 동안 한 일을 시간순으로 한 줄씩 남긴다. 사용자가 "그날 뭘 했는지"를 이 파일 하나로 본다.

1. 위치: 워크스페이스 루트의 `log/YYYY-MM-DD.md` 날짜 파일 하나. 월별 폴더를 만들지 않는다.
2. 쓰는 사람: 오케스트레이터만. 하위 세션은 쓰지 않고 보고에 외부 활동을 적는다([브리프](references/brief.md) 보고 형식). 오케스트레이터가 그것을 옮긴다.
3. 언제: 아래 사건이 생길 때마다 바로 덧붙인다. 하루 끝에 모아 쓰지 않는다.
   - `[work]` work 생성·보관
   - `[세션]` 하위 세션 시작·후속 지시·보관
   - `[확인]` 하위 세션 보고를 확인한 결과(통과·미확인·어긋남)
   - `[커밋]` 커밋 (`[PR]` PR 생성·병합·닫힘)
   - `[메시지]` 슬랙 등 외부로 보낸 메시지
   - `[결정]` 사용자 결정
4. 한 줄 형식: `- HH:MM [태그] <work> — <내용> (<링크>)`
   - work는 `work/` 아래 경로다. 없으면 `-`.
   - 링크: 세션은 `local_…` id(파일 밖에서도 읽히게 백틱), PR은 전체 URL, 커밋은 `<레포> <짧은 해시>`, 슬랙은 메시지 링크.
5. 시각 (KST, 24시간):
   - 커밋은 커밋 시각(`git log -1 --format=%cd --date=format:%H:%M <해시>`)을 쓴다.
   - PR은 생성·병합 시각(`gh pr view <번호> --json createdAt,mergedAt`, UTC이므로 +9시간)을 쓴다.
   - 보낸 메시지는 보낸 시각(보고에 적힌 시각 또는 슬랙 메시지 시각)을 쓴다.
   - 그 밖의 사건은 적는 시각(`date +%H:%M`)을 쓴다.
   - 실제 시각을 알 수 없으면 적는 시각 앞에 `~`를 붙인다(`~16:20`). 추정한 시각은 쓰지 않는다.
6. 파일:
   - 사건이 일어난 날짜의 파일에 쓴다. 파일이 없으면 첫 줄 `# YYYY-MM-DD`로 만든다.
   - 덧붙이기만 한다: `printf '%s\n' '<줄>' >> log/<날짜>.md`. 기존 줄을 고치거나 지우거나 정렬하지 않는다. `## 요약`이 생긴 뒤에는 아래 7을 따른다.
   - 늦게 보고된 사건은 실제 시각을 단 채 맨 아래에 붙인다. 그래서 시각이 앞 줄보다 이를 수 있다.
   - 잘못 적은 줄은 지우지 않고 바로잡는 줄을 덧붙인다(`[정정]`).
7. 하루 요약: 사용자가 따로 둔 하루 요약 예약 작업(예: 평일 19:30 KST)이 그날 파일 맨 아래에 `## 요약`을 덧붙인다. 오케스트레이터는 요약을 쓰지 않는다.
   - `## 요약` 뒤에는 줄을 붙이지 않는다. 요약이 생긴 뒤의 사건은 그 날짜 파일의 `## 요약` 줄 바로 위에 끼운다(Edit). 요약 내용은 고치지 않는다. 그 사건은 요약에 빠져 있으므로 줄 끝에 `(요약 후)`를 붙인다.
   - 날짜는 사건이 일어난 날을 따른다. 다음 날 파일로 넘기지 않는다.
   - 예약 작업은 앱이 켜져 있을 때만 돈다. 꺼져 있었으면 다음에 켤 때 앞 날짜 파일을 요약한다. 주말 파일은 요약하지 않는다.

```markdown
# 2026-11-04

- 09:59 [work] storefront/1104-order-export — work 생성, web-app `feat/order-export` (기준 origin/develop 1a2b3c4d)
- 10:02 [세션] storefront/1104-order-export — export-impl 시작: 주문 내보내기 구현 (`local_…`)
- 15:12 [커밋] storefront/1104-order-export — feat: 주문 내보내기 추가 (web-app 5e6f7a8b)
- 15:40 [PR] storefront/1104-order-export — #123 Draft 생성 → release (https://github.com/<org>/web-app/pull/123)
- 15:55 [확인] storefront/1104-order-export — export-impl 보고 확인: tsc·lint 재실행 통과, 화면 미확인
- ~16:20 [메시지] storefront/1104-order-export — 팀 채널에 #123 리뷰 안내 (<슬랙 링크>)
- 16:30 [결정] storefront/1104-order-export — 내보내기 파일 형식 결정 (사용자)
```

## 8. 맥락 유지와 이어받기

오케스트레이터의 대화 맥락은 언제든 요약되거나 끊긴다. 이어받을 세션이 허브만 읽고 같은 판단을 할 수 있게, 상태는 바뀌는 순간 디스크에 둔다. 주기적으로 모아 저장하지 않는다.

### 먼저 적고 행동한다

| 할 일 | 그 전에 적을 곳 |
|---|---|
| 사용자에게 결정을 묻는다 | `## 진행 중`에 `[사용자 대기]` + 질문 원문 |
| 하위 세션에 시작·후속 지시를 보낸다 | `## 세션` 명단 + `## 진행 중`에 `[세션 대기]` |
| 오래 걸리는 확인을 시작한다 | `## 진행 중`에 `[확인 중]` + 어디까지 봤는지 |

- 사용자가 대화에서 정한 것은 들은 즉시 결정 사항에 날짜와 함께 적는다. 보고할 때 몰아서 옮기지 않는다.
- 풀리면 `## 진행 중`의 그 줄을 지운다. 결과는 결정 사항·보고 기록·작업 로그(7절)로 옮긴다.
- 턴을 끝내기 전(`wrap_up` 전)에 확인한다: 이번 턴에 바뀐 결정·질문·보낸 메시지·세션 상태가 허브와 작업 로그에 다 있는가.
- claude-mem `work_state`는 쓰지 않는다. 상태는 허브 `task.md` 하나에 둔다. 세션 시작 때 주입되는 `work_state` 목록이 허브와 다르면 허브를 따른다.

### 이어받기

새 세션으로 오케스트레이터를 넘겨받았거나 맥락 요약을 받은 직후에는 아래 순서로 맞춰 본다. 요약이나 기억이 허브와 다르면 허브가 기준이다.

1. 자기 허브를 연다. 전담은 묶음 `task.md`(묶음 `AGENTS.md`는 자동 로드됨), 루트는 `work/orchestrator.md`.
2. `## 진행 중`부터 읽는다. 기다리던 질문·메시지가 무엇이었는지 안다.
3. `## 세션` 명단의 각 id를 `mcp__ccd_session_mgmt__get_session`으로 본다(보관·실행 여부). 새 세션은 앞 세션이 띄운 하위 세션이 `list_sessions {"linked": true}`에 나오지 않으므로 id로 직접 본다.
4. 오늘 작업 로그(`log/<날짜>.md`) 끝부분에서 허브에 아직 안 옮긴 사건이 있는지 본다.
5. 진행 중인 하위 work의 `task.md`를 읽는다. 끝난 work는 `## 마무리`만 읽는다.
6. 명단 상태와 실제 상태가 다르거나, 로그에만 있는 사건이 있으면 행동하기 전에 사용자에게 먼저 알린다.
7. 새 세션이 넘겨받았으면 허브의 `오케스트레이터:` 줄을 새 id로 고치고 작업 로그에 `[세션]`으로 남긴다.

## 하지 않는 일

- 훅 추가. 절차는 이 스킬과 루트 `AGENTS.md`로만 지킨다.
- claude-mem `work_state`에 작업 상태를 쓰는 일(8절).
- 작업 로그 자동화(예약 작업·훅·하루 끝 수집 스킬). 로그는 오케스트레이터가 사건마다 직접 적는다. 예외는 하루 요약 예약 작업 하나다(7절 7).
- agent-harness 플러그인(스킬·`bin/*`·훅), `AGENTS.md`, `CLAUDE.md` 수정. 고칠 점이 보이면 제안만 한다.
- 하위 세션의 노트만 보고 "끝났다"고 보고하는 일.
- 사용자 승인 없이 commit·push·PR·병합·배포·work 보관·세션 보관을 하는 일.
